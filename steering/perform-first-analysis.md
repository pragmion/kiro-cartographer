# Workflow: Perform First Analysis on a New Project

This guide walks you through the first complete analysis of a codebase using Kiro Cartographer. At the end you'll have steering files, skills, and architecture documentation that let Kiro work competently with your project from the first prompt.

## Prerequisites

- Kiro Cartographer is installed as a Power (see `POWER.md` for installation)
- You have a project directory you want to analyze

## Step 1: Optional — Prepare team conventions

If your team already has documented conventions (naming, formatting, architecture), have a template file created:

```
configure_profile with:
  action: "init"
  profileType: "team"
  rootPath: "<project path>"
```

Then edit `.cartographer/team-conventions.yaml` and adjust the values to match your team. If you don't have explicit conventions, you can skip this step — the Power will infer sensible defaults from the code.

## Step 2: Optional — Set up user profile

Personal preferences (comment style, output language) can be set globally:

```
configure_profile with:
  action: "init"
  profileType: "user"
```

The file is created at `~/.cartographer/user-profile.yaml` and applies to all projects.

## Step 3: Analyze the codebase

Start the full analysis:

```
analyze_codebase with:
  rootPath: "<project path>"
  incremental: false
```

Optional parameters for deeper analysis of specific areas:

```
analyze_codebase with:
  rootPath: "<project path>"
  focusAreas: ["api", "data-model", "build-pipeline"]
```

The analysis runs through all phases:
1. Directory structure and language distribution
2. Architecture patterns (MVC, Hexagonal, Layered, ...)
3. Data models and relationships
4. API endpoints (REST, GraphQL, gRPC, WebSocket)
5. Error handling strategies
6. State management
7. Build pipeline and CI/CD

During the analysis, the server emits progress notifications with the current step.

## Step 4: Save the analysis result

After completion you receive a JSON result. Save it for the artifact generation step:

```
Save the analysis as <project path>/.cartographer/last-analysis.json
```

## Step 5: Generate artifacts

```
generate_artifacts with:
  rootPath: "<project path>"
  analysisResultPath: "<project path>/.cartographer/last-analysis.json"
  artifactTypes: ["steering", "skills", "documentation"]
  conflictStrategy: "skip"
```

This produces:
- `.kiro/steering/coding-standards.md` — naming, formatting, imports
- `.kiro/steering/build-and-test.md` — build/test/lint commands
- `.kiro/steering/architecture.md` — layers and communication paths
- `.kiro/skills/*.md` — reusable patterns as skills
- `.kiro/docs/architecture.md` — architecture overview

## Step 6: Review the generated artifacts

Look at the generated files. Each carries a header:

```markdown
<!-- Generated by Kiro Cartographer v1.0.0 | Do not edit manually -->
```

If a file isn't a good fit:
- **Remove the header** → the file is treated as manually adopted and won't be overwritten on future generation runs.
- **Edit and keep the header** → your changes will be overwritten on the next `generate_artifacts`.
- **Delete it** → it will be regenerated on the next run.

## Step 7: Validation

Ask Kiro something project-specific, for example:
- "How would I add a new API endpoint here?"
- "What naming conventions does this project use?"
- "Where are database schemas defined?"

If the answers match the conventions visible in the code, the first analysis is complete.

## Common Issues

**No APIs detected** even though they exist: check whether the endpoints are defined in a framework the Power knows (Express, NestJS, Fastify, Koa). For exotic patterns you can add a manual steering file.

**Architecture pattern shows "low confidence"**: the Power found structural hints but too few for a confident match. In that case it's worth supplementing the generated `architecture.md` manually.

**Generated steering files are too generic**: set up team conventions (Step 1) and run `generate_artifacts` again. The conventions flow directly into the steering files.
